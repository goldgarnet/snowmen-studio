# 게임 구현 검증 케이스

이 문서는 Snowmen Studio 에디터와 같은 충돌·이동 메커니즘을 Godot 게임으로 옮길 때 사용하는 수동·자동 테스트 목록이다. 각 케이스는 **한 입력을 처리한 뒤의 최종 상태**와, 굴림이 발생하면 **tick 프레임 사이의 상태**를 모두 확인한다.

> 2026-11-03 팀 결정으로 포털과 주황 버튼·주황 벽을 게임에서 뺐다. P0-24·P0-29·P1-01 은 번호만 남기고 '삭제'로 표시했다. 예전 맵 코드의 해당 비트는 P2-06 으로 확인한다.

## 공통 표기

- 좌표는 `(row, col)`이며 왼쪽 위가 `(0, 0)`, 오른쪽으로 `col + 1`, 아래로 `row + 1`이다.
- `P3`: 크기 3 플레이어, `B1/B2`: 크기 1/2 눈덩이, `M1/M2/M3`: 크기 1/2/3 눈사람
- `K`: 블록, `W`: 일반 벽, `YB/YW`: 노란 버튼/벽
- `L↑/L→`: 위/오른쪽으로 발사하는 레이저, `F`: 눈송이, `H`: 구멍
- `A1`: 높이 1 가장자리 아치, `A2`: 높이 2 가장자리 아치
- 화살표는 플레이어 또는 굴림 그룹의 진행 방향이다.
- `movement`, `resolved`, `impact`, `turn-end`는 엔진 프레임 phase다.

## 테스트 실행 규칙

각 케이스에서 다음을 기록한다.

1. 초기 보드와 동적 타일 상태
2. 입력 순서와 입력 사이의 대기 여부
3. 최종 오브젝트 위치·크기·상태
4. 굴림이 있으면 tick별 위치, 버튼/벽 상태, 레이저·구멍 결과
5. 애니메이션을 켠 경우 프레임 순서와 각 entity의 위치 변화

입력이 막혔을 때는 `turnCount`, 녹기, 금 간 타일 붕괴가 진행되지 않는지도 확인한다. 반대로 눈덩이 파괴·분할처럼 플레이어가 제자리에 있어도 유효한 행동은 턴 종료 효과가 진행되어야 한다.

## P0 — 기본 이동과 충돌

### P0-01 빈 칸 한 칸 이동

- 초기: `P1`이 `(2,1)`, 주변에 장애물 없음
- 입력: `right`
- 기대: 플레이어가 `(2,2)`로 이동, 턴 1 증가, 굴림 없음
- 프레임: 이동 애니메이션을 켜면 일반 이동 frame과 최종 frame이 같은 입력에 대해 한 번씩만 생성

### P0-02 맵 경계에서 막힌 입력

- 초기: `P1`이 `(2,0)`에서 `left`
- 기대: 위치·상태 불변, `turnCount`와 녹기·균열 상태 불변, 레이저를 새로 발사하지 않음

### P0-03 void와 일반 벽 차단

- 초기: `P2` 앞 칸을 각각 `void`, `W`로 준비
- 입력: `right`
- 기대: 두 경우 모두 플레이어가 이동하지 않음. 두 보드는 동일한 차단 결과를 보여야 함

### P0-04 눈송이 흡수와 최대 크기

- 초기: `P1 → F → F → F`, 플레이어 최대 크기 3
- 입력: `right`, `right`, `right`
- 기대: 플레이어 크기가 `1 → 2 → 3`으로 증가하고 세 번째 이후 눈송이는 더 이상 크기를 증가시키지 않음. 소비된 눈송이는 차가운 타일이 됨

### P0-05 단일 오브젝트 밀기

- 초기: `P3 → B1`, 앞 칸은 비어 있음
- 입력: `right`
- 기대: 플레이어와 눈덩이가 각각 한 칸 이동하고, 눈덩이는 계속 굴림 상태가 됨

### P0-06 레이저 발사면에서 밀기 금지

- 초기: 오른쪽으로 발사하는 `L→`의 발사면 쪽에 플레이어 배치
- 입력: 레이저를 발사면 방향으로 밀려고 하는 입력
- 기대: 입력 실패, 레이저는 움직이지 않고 플레이어도 이동하지 않음
- 반대쪽에서 미는 입력은 레이저를 블록처럼 밀 수 있는지 별도로 확인
- 변형: 상자를 사이에 두면(레이저가 B·C 칸) 발사면 쪽에서도 레이저가 밀린다. 현행 유지(`bugs/B-025`, 2026-11-03)

## P0 — 눈사람 생성과 직접 힘

### P0-07 눈사람 합성 3종

- 초기: `P3 → B1 → B1`, `P3 → B1 → B2`, `P3 → B2 → B2`를 각각 준비하고 뒤에 단단한 받침 배치
- 입력: `right`
- 기대: 두 눈덩이가 각각 `M1`, `M2`, `M3`으로 합쳐짐. 플레이어는 A의 이전 칸으로 이동
- 금지: 완성될 눈사람 크기가 통과할 수 없는 아치를 합성 경계로 통과해서는 안 됨. 완성 크기는 B 칸 눈송이를 먹은 뒤 크기다(P0-30). 미는 플레이어가 통과할 수 없는 경계도 마찬가지(P0-28)

### P0-08 낮은 아치에서 큰 눈사람 합성 금지

- 초기: `P1 → B1 → B1`, A→B 경계에 `A1`, B 뒤에 단단한 받침
- 입력: `right`
- 기대: 완성될 `M1`과 미는 플레이어(크기 1)가 모두 `A1`을 지나므로 `M1` 합성
- 금지: 완성 크기가 2 이상인 조합(`B1 + B2` → `M2`, `B2 + B2` → `M3`)은 `A1`을 지나지 못하므로 합성하지 않음
- 변형: 같은 판에서 미는 플레이어가 `P2`·`P3`이면 플레이어가 `A1`을 지나지 못하므로 `M1`도 합성하지 않음(무반응, P0-28 · B-003). 2026-11-02 전에는 `P3`로도 `M1`을 만들었다
- 변형: B가 눈송이 위에 있으면 새 눈사람이 그 눈송이를 먹으므로 완성 크기가 하나 크다(P0-30)

### P0-09 크기 1 눈덩이 압착

- 초기: `P2 → B1 → W` 또는 맵 경계
- 입력: `right`
- 기대: 눈덩이가 사라지고 원래 칸에 눈송이가 생김. 플레이어는 이동하지 않지만 입력은 유효한 행동으로 처리되어 턴 종료 효과가 진행됨

### P0-10 크기 2 눈덩이 양방향 분할

- 초기: `P2 → B2`, 진행 방향에 단단한 받침, 위·아래 목적지는 빈 칸
- 입력: `right`
- 기대: `B2`가 진행 방향에 수직인 두 칸으로 `B1`, `B1` 분할
- 변형: 한쪽만 통과 가능하면 한쪽 눈덩이만 이동하고 원점에 다른 `B1`이 남음; 양쪽 모두 막히면 직접 힘에서는 원점에 `M1` 생성

### P0-11 힘은 직접 닿은 눈덩이에만

- 초기: `P3 → K → B1 → W`
- 입력: `right`
- 기대: 아무 일도 일어나지 않음. 블록 너머의 눈덩이는 부서지지도 쪼개지지도 않음

## P0 — 굴림 tick과 질량 충돌

### P0-12 굴림은 한 tick에 최대 한 칸

- 초기: `P3 → B1`, 오른쪽으로 긴 빈 직선
- 입력: `right`
- 기대: 엔진 계산은 한 입력에서 여러 tick을 처리하되, 각 `movement` frame의 해당 눈덩이 위치 차이는 최대 한 칸
- 애니메이션: 화면은 연속적으로 보이지만 중간 논리 상태를 건너뛰지 않음

### P0-13 더 무거운 굴림 그룹이 가벼운 장애물 그룹을 흡수

- 초기: 진행 그룹 질량 3, 앞의 정지 눈덩이 그룹 질량 1, 앞 칸 이동 가능
- 입력: 굴림을 시작하는 방향 입력
- 기대: 장애물 그룹과 현재 그룹이 각각 한 칸 전진한 뒤 하나의 굴림 그룹으로 병합. 다음 충돌 질량은 합계로 계산
- 변형: 장애물 그룹이 삼각 칸에 멈춘 공에서 꺾이면, 묶음은 거울 출구 쪽으로 한 칸 나가고 현재 그룹은 삼각 칸으로 따라 들어와 함께 굴러간다(P0-32)

### P0-14 같은 질량 탄성 충돌

- 초기: 진행 그룹과 정지 그룹의 총질량이 같음
- 기대: 진행 그룹은 정지하고 `impact` frame이 먼저 생성된 뒤 정지 그룹이 같은 방향으로 굴러감
- 금지: 정지 프레임이 중복되어 한 칸 이동이 두 번 지연되거나, 정지 그룹이 같은 tick에서 두 칸 이동하면 안 됨
- 삼각 칸에 멈춘 공을 칠 때의 그룹은 P0-26

### P0-15 더 무거운 장애물 그룹

- 초기: 진행 질량이 장애물 질량보다 작음
- 기대: 진행 그룹이 장애물에 도달한 위치에서 정지. 장애물은 움직이지 않음
- 변형: 장애물 앞 칸이 막혀 있으면 진행 그룹이 더 무거운 경우에도 양쪽 모두 정지

### P0-16 굴림 중 눈송이로 질량 변화

- 초기: 굴림 열차 앞 구성원이 `F`를 지나고, 그 뒤에 질량 비교가 필요한 장애물 배치
- 기대: 눈송이를 먹은 직후 해당 구성원의 크기와 그룹 총질량을 갱신한 뒤 다음 충돌을 판정
- 금지: 선두만 먹고 뒤쪽 구성원의 눈송이를 무시하면 안 됨

## P0 — 아치·벽·그룹 분리

### P0-17 열차의 뒤쪽 큰 공만 아치에 막힘

- 초기: 진행 방향으로 `B2 | B1 B1 B2`, 중간 경계에 `A1`
- 입력: 열차를 굴림
- 기대: 아치 뒤의 `B2`와 그 뒤쪽 prefix는 정지하고, 이미 아치 앞에 있는 `B1 B1 B2` suffix는 계속 굴러감
- 핵심: 선두 하나만 검사하지 말고 모든 구성원의 자기 경계를 검사

### P0-18 닫히는 노란 벽 안의 공 정지

- 초기: 여러 눈덩이가 일렬로 굴러가며, 한 공이 `YB`를 떠나는 순간 `YW`가 닫히도록 배치
- 기대: 벽 뒤의 공은 진입 불가, 벽 안의 공은 이탈 불가, 두 공과 뒤쪽 prefix는 정지. 벽보다 앞선 suffix만 계속 굴러감
- 확인: 별도 “가장 앞 막힌 공” 예외 없이 공별 `canCross`와 점유 의존성만으로 같은 결과가 나와야 함

### P0-19 닫힌 색상 벽은 받침이 됨

- 초기: `P → B1 → YW` 및 벽 너머에 빈 공간
- 입력: `right`
- 기대: 눈덩이가 닫힌 벽에 막혀 이동하지 않거나, 압착·분할의 단단한 받침으로 인식됨
- 변형: `YB`가 눌려 벽이 열리면 다음 tick부터 통과 가능

### P0-20 터널·삼각 벽·void 혼합 분리

- 초기: 같은 굴림 열차의 각 구성원이 서로 다른 통과 조건(터널, 삼각 벽의 닫힌 변, void, 아치)을 만남
- 기대: 각 구성원별 `canCross` 결과와 앞 공의 칸 비움 여부에 따라 이동 suffix가 결정됨. 지형 종류별 특수 예외를 추가하지 않아도 동일한 원칙으로 판정

## P0 — 버튼·레이저·구멍

### P0-21 마지막 노란 버튼과 레이저의 같은 tick 판정

- 초기: 플레이어가 첫 `YB`를 점유하고, 굴러가는 눈덩이가 마지막 `YB`에 도착하면 `YW`가 열리며 `L↑`가 플레이어를 겨냥하도록 배치
- 기대 프레임:
  1. `movement`: 눈덩이가 마지막 버튼 위에 도착
  2. `resolved`: 노란 벽이 열린 상태에서 레이저가 플레이어를 제거
  3. 이후 눈덩이의 후속 tick은 계속 진행
- 최종: 플레이어가 없거나 영혼 이전, 눈덩이는 자체 정지 조건까지 이동

### P0-22 게임 오버 후 활성 굴림 유지

- 초기: 위 케이스처럼 플레이어가 최종 사망하지만 눈덩이는 긴 직선에 있음
- 기대: 상태는 `gameover`가 되지만 이미 시작된 굴림 frame은 모두 생성되고 눈덩이는 벽·경계·충돌까지 계속 진행
- 금지: 게임 오버를 이유로 굴림 루프나 애니메이션을 조기 종료하면 안 됨

### P0-23 굴림 중 구멍

- 초기: 단일 눈덩이의 다음 칸이 `H`
- 기대: 해당 tick에서 눈덩이가 구멍 칸으로 이동한 뒤 제거되고, 후속 굴림은 종료
- 변형(2026-10-26 변경): 플레이어가 빈 `H`로 걸어 들어가면 유효한 이동(턴 +1)이고, 같은 턴의 구멍 처리에서 몸이 빠져 사라진다. 영혼은 턴 종료 녹기보다 먼저 `H`에서 가장 가까운 눈사람으로 옮겨 가고(P1-05 규칙, 크기·`isMelting` 보존), 후보가 없으면 `gameover`, 새 몸이 활성 목표 위면 `cleared`
- 변형: `H`는 그대로 남고 식지 않는다. 다음 몸이 걸어 들어가도 또 빠진다

### P0-24 (2026-11-03 삭제) 일반 이동 포털과 굴림 포털

포털을 게임에서 뺐다. 예전 맵 코드의 포털 칸은 평범한 바닥이다(P2-06).

### P0-25 레이저 차단 순서

- 초기: 레이저 빔 경로에 `W`, 닫힌 `YW`, 삼각 벽을 각각 배치
- 기대: 일반 벽과 닫힌 노란 벽은 뒤의 플레이어·눈덩이를 보호한다. 빔은 방향에 관계없이 삼각 벽을 통과해 뒤의 오브젝트에 닿는다.
- 변형: 터널과 아치는 레이저를 막지 않음

### P0-26 삼각 칸 공의 꺾인 묶음 (B-001)

- 초기: `P2 → B1 → 빈 칸 → ◥B1`(오른쪽→아래로 꺾는 삼각 칸 안에 멈춘 공), 그 거울 출구(아래 칸)에 `B1`
- 입력: `right`
- 기대: 장애물 그룹은 삼각 칸에서 거울처럼 꺾여 출구 쪽으로 이어진다. `◥B1`과 출구의 `B1`이 한 묶음(질량 2)이므로 굴러온 공(질량 1)이 삼각 칸 앞에서 멈추고 아무것도 움직이지 않음. `impact` 없음

- 초기: 플레이어가 목표 타일 위에 있지만 같은 턴에 레이저 빔에 노출
- 기대: 레이저 사망이 먼저 처리되고, 살아남은 플레이어가 없으면 클리어하지 않음
- 범위: 같은 순간(이동 직후 판정, 굴림의 같은 tick) 안의 순서다. 굴림은 클리어가 정해진 tick에서 끝나므로 뒤 tick의 빔은 없다(P0-27 · B-027)

### P1-09 클리어 조건의 초록 버튼

- 초기: 목표 타일과 초록 버튼 1개 이상
- 기대: 플레이어가 목표에 있어도 모든 초록 버튼이 덮이지 않으면 `playing`. 모든 버튼을 덮은 뒤 목표에 도착해야 `cleared`
- 초록 버튼이 없으면 목표 위 플레이어만으로 클리어
- 굴림 중 한 tick이라도 모든 버튼이 덮이고 플레이어가 목표 위면 클리어(P0-27)

### P1-10 동일 입력 결정성

- 초기: 삼각 반사·버튼·굴림이 섞인 보드
- 입력: 동일한 입력 배열을 두 번 실행
- 기대: 최종 Level, status, frame phase 순서, 각 frame의 entity 위치·크기가 모두 동일

## P1 — 프레임·애니메이션 재생

### P1-11 프레임 phase 순서

- 초기: 일반 굴림, 구멍, 버튼, 레이저가 한 입력에서 발생하도록 준비
- 기대: 위치 변경마다 `movement → resolved`, 탄성 질량 충돌에는 `impact`가 접촉 상태 뒤에 추가, 모든 운동 종료 후 `turn-end`
- 금지: 엔진 상태를 바꾸기 위해 UI가 frame을 재계산하거나 순서를 재정렬하면 안 됨

### P1-12 애니메이션 끄기와 켜기 결과 동등성

- 초기: 동일 보드와 동일 입력 배열을 준비
- 실행 A: 애니메이션 끄기
- 실행 B: 애니메이션 켜기
- 기대: 표시 과정은 달라도 최종 Level, status, turn 수, undo 기록은 완전히 동일

### P1-13 재생 중 토글 끄기

- 초기: 여러 movement frame이 발생하는 입력
- 실행: 첫 movement transition 도중 애니메이션 끄기
- 기대: 남은 타이머를 취소하고 이미 계산된 최종 Level·status를 즉시 표시. 입력 1회와 undo 1회만 기록

### P1-14 속도 슬라이더

- 초기: 이동 frame이 2개 이상인 보드
- 실행: 0.1배, 1배, 5배로 각각 재생
- 기대: 논리 프레임과 최종 상태는 동일하고, movement 기본 시간은 각각 `1500ms`, `150ms`, `30ms`로 계산
- impact 기본 80ms도 같은 배율로 `800ms`, `80ms`, `16ms`가 됨

### P1-15 motion ID 연속성

- 초기: 같은 눈덩이가 여러 tick 이동하고, 다른 눈덩이는 생성·분할됨
- 기대: 계속 존재하는 entity는 frame 사이 동일한 `motionId`, 새로 생성된 절반·눈사람은 새 ID. Grid는 ID가 같은 객체만 FLIP 보간
- 사례 P1-15a: `P2 → B2 → W`로 쪼갠 위쪽 반쪽이 이웃 `B1`을 한 칸 밀어내고 그 칸에 들어감 → 밀려난 공은 원래 ID(`snowball:1:1`), 새 반쪽은 새 ID(`snowball:1:1~2`). 한 frame 안에서 ID는 물체마다 하나(B-009)
- 사례 P1-15b: 플레이어 시작 칸에 눈사람을 밀어 넣은 뒤 구멍에 빠져 영혼이 그 눈사람으로 옮겨 감 → 새 몸은 옛 몸(`player:1:1`)과 다른 ID를 받아 몸이 바뀐 것으로 인식됨(`soulChangedBody`, 키 반복 막기 — B-009)

### P1-16 특수 이동은 가짜 경로를 보이지 않음

- 초기: 삼각 블록 반사, 영혼 이전이 발생
- 기대: 일반 한 칸 이동만 보간하고 반사처럼 여러 칸을 건너뛴 이동은 즉시 전환. 통과하지 않은 타일을 가로질러 슬라이드하지 않음

## P2 — 안전성·성능·도구 연동

### P2-01 삼각 반사 무한 루프

- 초기: 삼각 반사 구조가 같은 위치를 반복하게 구성(예: 네 삼각 벽이 사각형 고리를 이룸)
- 기대: `width × height × 4 + 16`과 같은 안전 한도에서 루프가 종료되고 브라우저/Godot 프레임이 멈추지 않음
- 최종 상태는 결정적인 정지 상태 또는 안전한 중단 상태여야 함

### P2-02 동시 이동 덮어쓰기 방지

- 초기: 세 오브젝트 연쇄 이동 `P → A → B → C → 빈 칸`
- 기대: 가장 앞의 C부터 이동하고, 모든 오브젝트가 한 칸씩 정확히 이동. P/A를 먼저 기록해 오브젝트가 사라지거나 중복되지 않음

### P2-03 입력 잠금

- 초기: 애니메이션 재생 중인 보드
- 실행: 방향키, 대기, undo, reset, M을 연속 입력
- 기대: 재생 중에는 추가 turn·undo·영혼 이동이 생성되지 않고, 재생 종료 후 다음 입력 한 번만 처리

### P2-04 프레임 스냅샷 불변성

- 초기: 여러 tick이 발생하는 보드
- 실행: 첫 frame을 참조한 뒤 다음 frame을 계산
- 기대: 이전 frame의 Level이 이후 계산으로 변경되지 않음. Godot에서는 deep copy 또는 immutable snapshot 사용

### P2-05 저장된 풀이 재현

- 초기: 맵 코드와 입력 문자열을 저장
- 실행: 입력 문자열을 새 게임 인스턴스에서 재생
- 기대: 동일한 최종 Level·status·turn 수. 맵 코드가 변경되면 기존 풀이를 무효화

### P2-06 포털·주황 비트가 남은 예전 맵 코드 (2026-11-03)

- 초기: 포털과 주황 버튼·주황 벽을 뺀(2026-11-03) 전에 만든 맵 코드. v5 확장 타일 플래그 5비트 중 주황 버튼(4번)·주황 벽(3번)·포털(0번) 비트가 켜져 있음
- 기대: 코드는 그대로 열리고 그 칸은 평범한 바닥이다. 그 칸의 다른 타일 정보(목표·따뜻함·아치)와 뒤 섹션(삼각 블록·삼각 칸 물체·void)은 그대로다. 다시 저장하면 세 비트는 0이고, 남는 v5 정보가 없으면 확장 자체가 빠진다
- 사례: 7×3 `P2 · 포털 · 주황 버튼 · 주황 벽 · 바닥 · 포털 · 목표`(예전엔 2수에 클리어) → 순간이동 없이 6수 걸어 클리어. 팀 맵 「Maze」(목표 칸의 주황 벽이 바닥)·「one way」(양 끝 포털이 바닥)
- 금지: 디코드 실패, 그 비트 때문에 뒤 섹션이 어긋남, 다시 저장한 코드에 비트가 남음
- Studio 자동 테스트: `test/engine/cases/legacy-portal-orange-codes.scenario.ts`. 테스트 워크벤치 P2-06

## 구현 체크 순서

Godot 초기 구현은 다음 순서로 진행하면 원인 추적이 쉽다.

1. P0-01 ~ P0-11: 한 칸 이동·밀기·합성·분할
2. P0-12 ~ P0-20: tick·질량·아치·색상 벽
3. P0-21 ~ P0-25: 즉시 환경 반응
4. P0-26 ~ P0-32: 삼각 칸 묶음 질량·굴림 중 클리어·합성 경계의 플레이어 크기·눈송이로 커지는 눈사람·지형 받침·삼각 칸 공을 데리고 꺾이는 더 무거운 굴림
5. P1-02 ~ P1-10: 턴 종료·영혼·클리어·결정성
6. P1-11 ~ P1-16: 프레임과 화면 재생
7. P2 전체: 루프 방지·불변성·저장(예전 맵 코드 포함)·입력 잠금

각 그룹을 통과할 때마다 “최종 상태가 맞다”뿐 아니라, **어느 tick에서 버튼·벽·레이저·구멍이 바뀌었는지**를 로그 또는 디버그 오버레이로 확인한다. 최종 위치만 맞고 중간 frame이 틀리면 이후 버튼 연쇄와 애니메이션이 다시 깨질 가능성이 높다.
